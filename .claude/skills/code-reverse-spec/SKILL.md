# 코드 역설계 → spec 조각 추출

목표: 담당 영역의 코드를 읽어, 기획문서를 쓸 사람이 **코드를 다시 안 봐도 되도록** 검증된 사실을 조각으로 남긴다.

## 왜 이렇게 하는가

기획문서가 코드보다 뒤처지면(drift) 문서를 믿고 작업한 결과가 어긋난다. 그래서 문서를 코드에서 다시 길어 올린다. 이 단계의 가치는 **추측을 섞지 않는 것** — 추측이 한 줄 들어가면 그 위에 쌓인 문서 전체의 신뢰가 깨진다.

## 절차

1. **전수로 읽는다.** 담당 파일을 처음부터 끝까지 읽는다. 큰 파일은 공개 인터페이스(export·API·이벤트)와 데이터 계약을 먼저, 내부 헬퍼는 그다음.

2. **계약을 먼저 고정한다.** 이 영역이 바깥에 노출하는 것부터 적는다:
   - 서버: HTTP method·path·요청/응답 JSON shape(필드명·타입·옵셔널 여부)
   - 클라 모듈: export 함수·클래스 시그니처(인자·반환), 발신/수신 이벤트, 읽고 쓰는 전역·localStorage·DOM id
   계약은 다음 영역(소비자)이 의존하는 면이라 가장 정확해야 한다.

3. **동작을 근거와 함께 적는다.** "무엇을 한다 + 트리거 + 분기 조건 + 부작용 + (file:line)". 근거 없는 단정 금지.

4. **흐름을 단계로.** 상태 전이·호출 순서·폴링 주기가 있으면 번호 단계로 적는다(독자가 시간순으로 따라가게).

5. **경계를 양방향으로.** 노출(다른 영역이 쓰는 것)과 의존(이 영역이 쓰는 것)을 분리해 적는다 — 합성 단계에서 영역을 잇는 접합부다.

6. **모르는 건 모른다고.** 호출 여부·실행 경로가 코드로 안 보이면 "정적으로 확인 불가". 의도 추측은 "추정" 절에만.

## 사실 vs 추정 구분 (핵심)

| 분류 | 기준 | 기록 위치 |
|------|------|-----------|
| 사실 | 코드에 그렇게 적혀 있음(file:line 제시 가능) | §4 핵심 동작 |
| 계약 | export/API/이벤트로 외부에 노출된 면 | §3 데이터 계약 |
| 추정 | 코드로 확정 못 하나 정황상 그럴 것 | §7 추정·미확정 |
| drift | 기존 문서와 코드가 다름 | §7 (차이 명시) |

## 출력

`_workspace/spec_chunks/{area}.md` 에 spec-cartographer 정의의 7절 구조로 Write 한다. 한 영역 = 한 파일.

## 하지 말 것

- 영역 밖 파일까지 분석(범위 침범 — 다른 cartographer 담당).
- 코드 개선 제안(여기선 사실 추출만; 개선은 별도 하네스).
- 요약으로 퉁치기("렌더링을 한다" 식 — 무엇을 어떤 조건에 하는지가 빠지면 가치 없음).
